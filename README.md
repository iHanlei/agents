# AGENTS.md — Vue 3 + TypeScript + Vite 前端项目

本文档是本仓库中 Codex 的项目级执行约定。目标是在保持现有架构与行为的前提下，交付可审查、可验证、可维护的生产代码。

## 1. 指令优先级与基本原则

- 遵循顺序：用户当前明确要求 > 当前目录更深层的 `AGENTS.override.md` / `AGENTS.md` > 本文件 > 仓库现有代码与工具配置。
- 本文件描述默认约定；若与 `package.json`、锁文件、TypeScript、ESLint、Prettier、Vite 或测试配置冲突，以仓库中可执行的现有配置为准，并在交付说明中指出差异。
- 不猜测代码行为。修改前先读取目标文件、直接依赖、相关类型、测试及配置。
- 采用最小充分改动：只处理任务范围，不顺手重构、不批量格式化、不改无关文件。
- 保持向后兼容。除非用户明确要求破坏性变更，否则不得删除或重命名公共 API、组件 props/emits、路由、存储字段或导出。
- 不覆盖或清理用户已有的未提交改动。发现冲突时先停止相关编辑并说明。
- 未经用户明确要求，不创建提交、不推送分支、不发起 PR。

## 2. 技术栈与仓库事实

- 框架：Vue 3，优先 Composition API 与 `<script setup lang="ts">`；新代码禁止引入 Options API。
- 语言：TypeScript 严格模式；新代码必须兼容 `strict` 与 `noUncheckedIndexedAccess`。
- 构建：Vite。
- 路由：Vue Router 4；使用 history 模式和路由级懒加载，除非仓库现状另有明确约定。
- 状态：Pinia；新 store 使用 setup store / composition 风格。
- 包管理器：根据锁文件确定。存在 `pnpm-lock.yaml` 时只使用 pnpm，不使用 npm 或 yarn。
- 样式：沿用项目已有 Sass、CSS Modules、UnoCSS 或 Tailwind 方案，不新增并行样式体系。
- 国际化：沿用 vue-i18n；目标语言为 `en`、`pt-BR`、`hi`、`zh-Hant`。
- 测试：Vitest + `@vue/test-utils`，关键用户路径使用 Playwright。

开始任务时先核实上述能力是否已在仓库中配置。不得仅为满足本文档而擅自安装依赖或重写配置。

## 3. 命令发现与执行

先读取 `package.json` 的 `scripts` 和锁文件，再执行仓库实际存在的命令。标准脚本优先为：

| 用途 | 首选命令 |
| --- | --- |
| 开发服务器 | `pnpm dev` |
| 生产构建 | `pnpm build` |
| 本地预览 | `pnpm preview` |
| 代码检查 | `pnpm lint` |
| 自动修复 | `pnpm lint:fix` |
| 格式化 | `pnpm format` |
| 类型检查 | `pnpm typecheck` |
| 单元/组件测试 | `pnpm test:unit` |
| E2E 测试 | `pnpm test:e2e` |
| 交互式提交 | `pnpm commit` |

- 不运行不存在的脚本，不自行臆造替代参数。
- 自动修复和全量格式化可能改动无关文件，默认只对任务文件执行定向修复；执行前后检查 diff。
- 代码改动的默认验收链：`pnpm lint` → `pnpm typecheck` → 与改动直接相关的测试。
- 影响构建配置、路由、公共入口、依赖图或产物行为时，再运行 `pnpm build`。
- 仅当改动涉及关键用户路径、浏览器行为或用户明确要求时运行相关 E2E；需要外部服务、凭据或浏览器环境时先说明前置条件。
- 每项检查都记录结果。若因环境、既有失败或缺少脚本无法执行，明确报告“未验证”的项目、原因和建议命令，不得声称全部通过。

## 4. 目录与职责

```text
src/
  api/          # 请求实例、模块化 API 函数与边界类型
  assets/       # 图片、字体等静态资源
  components/
    base/       # 无业务或弱业务依赖的通用组件
    business/   # 面向业务场景的复合组件
  composables/  # 可复用的有状态 Vue 逻辑
  layouts/      # 页面布局
  locales/      # 国际化资源
  router/       # 路由与守卫
  stores/       # Pinia stores
  styles/       # 全局样式、token、变量与 mixin
  types/        # 跨模块共享类型
  utils/        # 无 Vue 依赖的纯函数
  views/        # 路由页面
tests/
  unit/         # 单元与组件测试，或遵循源码同目录测试约定
  e2e/          # Playwright 测试
```

- 优先遵循仓库已经形成的目录模式；不得为了匹配上表迁移现有文件。
- 新文件放入职责最接近的已有目录，不随意增加顶层目录。
- 页面通常由 `views/` 页面、路由配置以及按需存在的 API/store/composable 组成；避免把请求、状态与复杂业务规则全部塞进页面组件。
- 仅被一个组件使用的逻辑不必强行抽象；出现真实复用、复杂状态流程或可独立测试价值时再提取 composable/util。

## 5. Vue 组件规范

- 新组件使用 `<script setup lang="ts">`，SFC 顺序保持为 `<script setup>` → `<template>` → `<style>`。
- 使用类型参数声明 `defineProps` 与 `defineEmits`；类型需要复用时定义命名 `interface` 或 `type`，禁止裸 `any`。
- Vue 版本支持时可用 `defineOptions({ name: '...' })`；否则依赖多词文件名的组件名推断或沿用项目既有方案，不为显式 name 引入第二个 script 块。
- props 提供稳定默认值时使用与当前 Vue 版本兼容的 `withDefaults` 或响应式解构方式。不得改写传入 props。
- emit 名称遵循现有项目约定；处理函数使用 `onSubmit`、`onPageChange` 等 `on + 动词/行为` 命名。
- 派生数据优先 `computed`，副作用使用 `watch` / `watchEffect` 并处理清理；避免用 watcher 模拟可直接表达的派生状态。
- 异步 UI 必须考虑 loading、empty、error、success 以及重复提交；存在竞态时使用取消、请求序号或最新结果保护。
- 列表使用稳定业务 key，禁止在可重排列表中使用数组下标作为 key。
- 不滥用 `nextTick`、深度 watch、`forceUpdate` 或直接 DOM 操作；确需使用时说明约束。
- 样式是否 `scoped`、CSS Modules 或 utility-first 以相邻组件为准。全局 token 和共享规则放入既有 `styles/` 体系，避免无意污染。
- 保持 SSR/缓存组件语义（若项目使用）；定时器、监听器、observer 和外部实例必须在卸载时释放。

## 6. TypeScript 规范

- 禁止 `any`。与不可信外部数据交互时使用 `unknown` 并通过类型守卫、schema 或明确校验进行收窄。测试 mock 也优先保持类型安全。
- 数组索引、字典索引及可选字段访问必须处理 `undefined`。非空断言仅限由紧邻逻辑可证明且类型系统无法表达的场景。
- 导出的公共函数与 composable 写显式返回类型；局部简单回调允许类型推断。
- 对象形状通常使用 `interface`，联合、映射、条件与函数类型通常使用 `type`；以表达准确和仓库一致性为准，不做机械转换。
- 避免普通 `enum` 和 `const enum`；优先字符串字面量联合，或 `as const` 对象加值类型，以兼容 Vite/isolated modules 工具链。
- 不使用 `@ts-ignore`。`@ts-expect-error` 仅可用于确需断言编译错误的类型测试，或有明确上游缺陷且附原因、跟踪信息的临时兼容代码。
- 类型断言不能代替运行时校验；API、本地存储、URL 参数和第三方消息均视为不可信输入。
- 不重复定义已有领域类型。先搜索相同模型、请求/响应类型和工具类型。

## 7. 状态、路由与请求边界

### Pinia

- 新 store 使用 `export const useXxxStore = defineStore('xxx', () => { ... })`。
- 组件读取 store 时按需使用 `storeToRefs` 保留响应性。
- 业务状态变更通过 store action 或 store 暴露的明确方法完成；不要在多个组件中散落同一状态转换规则。
- store 不持有可由现有 state/getter 稳定推导的数据，除非缓存有已验证的性能收益。
- 测试之间必须重置 store，避免全局状态泄漏。

### Router

- 页面路由默认懒加载；route name、meta 和参数类型保持一致。
- 导航守卫必须有明确终止路径，避免循环重定向、重复导航与未决 Promise。
- 权限判断优先集中在既有守卫/权限层，不只依赖按钮隐藏。
- query、params 和重定向目标视为外部输入，使用前校验；禁止形成开放重定向。

### API

- 所有 HTTP 请求通过 `src/api/request.ts` 或仓库现有等价请求实例。
- 业务请求放入 `src/api/<module>.ts`，导出类型化函数；组件和 composable 不直接调用 axios/fetch 底层实例。
- 统一处理 token、超时、错误规范化及通用提示；业务层只处理具有业务语义的分支。
- `catch` 不得吞错或无依据返回 `null`。若降级是产品要求，返回可辨识的结果类型并记录/展示适当信息。
- 不在日志、错误提示、URL 或分析事件中暴露 token、凭据、个人信息及完整敏感响应。
- GET 等幂请求可按现有策略重试；创建、支付、提交等非幂等请求未经幂等设计不得自动重试。

## 8. i18n、可访问性与产品文案

- 所有用户可见文案，包括标题、占位符、空状态、校验提示、toast、`alt`、`aria-label` 和确认文案，都使用 vue-i18n；禁止硬编码任意界面语言。
- key 按领域分层，例如 `common.save`、`order.status.paid`、`login.errors.invalid`，避免无语义扁平 key 和把整句英文当 key。
- 新增或修改 key 时同步维护 `en`、`pt-BR`、`hi`、`zh-Hant`。复数、日期、数字、货币与插值使用 vue-i18n 能力，不手工拼接语序。
- 删除 key 前搜索静态和动态引用；无法证明未使用时不删除。
- 优先原生语义元素。所有交互必须可通过键盘完成，并具有可见焦点；图标按钮必须有可访问名称。
- 表单控件关联 label 与错误信息；异步状态按需使用 `aria-live` / `aria-busy`；Modal 处理焦点进入、焦点陷阱和关闭后焦点恢复。
- 颜色对比、减少动画偏好和触摸目标尺寸遵循项目设计系统及 WCAG 2.1 AA 的既有目标。

## 9. 样式与前端性能

- 使用现有 design token、组件变量和断点，不复制魔法颜色、间距或 z-index。
- 不用 `!important` 解决可通过层级或作用域修正的问题；不使用过深选择器。
- 保持移动端、桌面端和内容增长场景可用；至少考虑长文本、四语言长度差异和空数据。
- 避免在模板或高频渲染路径中创建昂贵对象、排序大数组或执行重复查找。
- 大组件、重资源和非首屏功能按现有策略懒加载；新增依赖前评估包体积、tree-shaking、维护状态和已有替代方案。
- 图片明确尺寸以减少布局偏移，按用途选择格式与懒加载；不得直接引入 node_modules 中不必要的大资源。
- 性能优化必须基于可复现证据，记录优化前后指标；不以可读性换取未经测量的微优化。

## 10. 测试规范

- 对本次行为变更补充与风险匹配的测试，不要求为了数字覆盖率编写无效测试。
- utils、复杂 composable、store action/getter、数据转换与错误分支优先单元测试。
- 组件测试覆盖用户可观察行为、props、emits、插槽、加载/错误状态和关键可访问交互；避免断言 Vue 内部实现细节。
- API 测试覆盖请求参数、响应映射和错误规范化，不发真实网络请求。
- E2E 聚焦登录、权限、主流程、支付/提交等关键路径；优先使用稳定角色和可访问定位器，禁止依赖脆弱 CSS 层级或固定延时。
- 测试名称推荐 `it('should <expected behavior> when <condition>')`，也可沿用仓库现有语言和命名风格。
- 修复缺陷时，条件允许应先添加能复现失败的回归测试，再实现最小修复，并确认测试由失败转为通过。
- 测试必须可隔离、可重复，控制时间、随机数、网络和持久化状态；不得使用真实生产凭据或生产数据。
- 修改公共组件、API 层、共享类型或 store 时，搜索调用方并运行受影响测试；不得只验证新增测试。

## 11. 安全与隐私

- 不读取、展示、复制或提交不属于任务所需的秘密信息。输出中对 token、cookie、邮箱、手机号和个人数据脱敏。
- 禁止硬编码 API 地址、密钥、token、业务状态码及环境专属值；使用现有配置、常量和领域映射。
- 渲染富文本或 HTML 时默认不可信；避免 `v-html`。确需使用时必须采用项目认可的消毒策略并说明数据边界。
- 防止 XSS、开放重定向、路径/URL 注入、原型污染和不安全本地存储。前端权限控制不能替代服务端鉴权。
- 外链按场景限制协议；使用 `target="_blank"` 时加入适当 `rel`。
- 不将敏感数据持久化到 localStorage、日志、监控 breadcrumb 或客户端错误详情，除非项目已有经审查方案。

## 12. 依赖、配置与生成文件

- 禁止擅自新增或升级 production dependency、devDependency。确有必要时先说明：用途、现有替代方案、包体积/安全影响和版本选择，获得用户确认后再执行。
- 未经用户明确要求，不修改 `.env*`、生产域名、部署凭据、CI secret、证书和线上 Vite 配置。
- 只有在获准安装或更新依赖时才允许修改锁文件，并与 manifest 变更一同提交。
- 不手工编辑由工具生成的客户端、类型、路由或资源文件；找到生成源与脚本，从源头修改并重新生成。
- 不提交 `node_modules/`、`dist/`、覆盖率、日志、截图、trace、临时文件或本地 IDE 状态，除非它们是用户明确要求的交付物。

## 13. 工作流

### 动手前

1. 检查仓库状态与当前 diff，识别用户已有改动。
2. 读取目标文件、相邻实现、调用方、类型、测试和相关配置。
3. 用一句话复述任务目标和可验证的完成条件。
4. 预计修改超过 3 个文件、跨模块或存在兼容性风险时，先列出简短改动清单；不因低风险、显而易见的细节阻塞执行。

### 实施中

1. 按可独立验证的小步修改。
2. 每完成一个行为单元就运行最相关的快速检查。
3. 持续检查 diff，避免格式噪音和越界改动。
4. 发现需求与现有架构冲突时，用代码证据说明；只有会显著改变产品行为、数据或公共 API 的选择才请求用户决策。

### 交付前

1. 搜索并移除临时 `console.log`、`debugger`、注释掉的实现、测试专用开关和占位文案。
2. 审查最终 diff：正确性、边界条件、类型、错误处理、i18n、可访问性、安全、性能和测试。
3. 执行验收链并确认没有因本次改动产生新警告。
4. 最终回复简洁列出：完成内容、关键文件、验证命令及结果、任何未验证项或剩余风险。不得隐藏失败。

## 14. Git 与变更安全

- 只修改任务相关文件；提交前使用 diff 确认范围。
- 不使用会丢失工作成果的命令，例如 `git reset --hard`、宽范围 `git checkout --`、`git clean` 或强制推送，除非用户明确指定准确目标并授权。
- 不修改、暂存、提交或回滚无法确认归属的现有改动。
- 提交信息遵循 Conventional Commits：`feat|fix|refactor|docs|style|test|chore(scope): 描述`。
- 只有用户明确要求提交时才运行提交命令；提交中只包含本任务文件。

## 15. Code Review Rules

执行代码审查时默认只读，按严重程度输出可操作发现，先列问题再给摘要。

- 优先发现：运行时错误、行为回归、数据丢失、安全/隐私问题、竞态、错误边界、类型漏洞、兼容性和缺失测试。
- 每条发现包含：严重级别、文件与精确行、触发条件、实际影响、建议修复方向。
- 不把纯个人偏好或已由自动格式化工具覆盖的风格问题当作主要发现。
- 若没有发现，明确写“未发现可操作问题”，并说明仍未覆盖的测试或环境风险。
- 不在“审查”任务中直接修改代码；只有用户同时要求修复时才实施改动。

## 16. 执行方式

- 默认由当前代理端到端完成分析、实现、审查与验证，不创建或委派子代理。
- 将复杂任务拆成可独立验证的小步骤，在同一会话中依次完成并持续同步进度。
- 只有用户在当前任务中明确要求使用子代理时，才允许临时委派。

## 17. 完成定义

任务仅在以下条件满足时视为完成：

- 用户要求的可观察行为已实现，且无已知越界变更。
- 相关类型、错误、loading/empty 状态、i18n 和可访问性已处理。
- 与风险匹配的测试已新增或更新，并验证调用方。
- lint、typecheck、相关测试按仓库能力通过；必要时 build/E2E 通过。
- 最终 diff 无秘密、调试代码、生成垃圾、无关格式化和意外锁文件变更。
- 任何无法验证的内容均已明确披露，不以推测代替结果。
