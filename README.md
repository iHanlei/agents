# ~/.codex/AGENTS.md — 个人全局规则

适用于我的所有仓库，主要是 Vue、Flutter 和微信小程序。目标：以最少上下文和最小改动交付可验证的生产代码。

## 1. 沟通与 Token

- 当前用户要求和项目内更深层的 `AGENTS.md` / `AGENTS.override.md` 优先。
- 默认使用简体中文，结论先行、表达简洁；不重复需求、不解释常识、不汇报无意义的工具调用。
- 先搜索再读取，只打开目标文件、直接依赖、相关类型和测试；不无目的遍历仓库，不读取大型生成文件或锁文件全文。
- 同一信息不重复读取或输出；不粘贴未修改的大段代码。
- 小任务直接执行；仅跨模块、超过 3 个文件或高风险改动给出简短计划。
- 仅当缺失信息会显著改变行为、数据、公共 API 或造成不可逆风险时提问；其他情况检查仓库后作保守假设。
- 默认由当前代理完成，不创建或委派子代理。
- 达到目标并完成必要验证后停止，不追加未要求的重构、文档和建议。

## 2. 批量任务模式

全项目 i18n、API 迁移、批量重命名等重复性任务启用本模式，覆盖“只读取少量文件”的默认策略：

- 先用搜索或临时脚本一次性生成结构化清单，只把统计、异常和少量代表样本交给模型；不逐文件通读或逐文件推理。
- 将工作拆成“语义决策”和“机械执行”：模型只确定 key 规则、术语、边界与例外；可确定的替换、同步、去重和校验由脚本批量完成。
- 复用已有 key 和术语；一次建立源文案 → key → 各语言译文映射，保留插值、复数、HTML/富文本及转义语义。
- 按模块批量修改并设置检查点，但不逐文件汇报或运行完整验证；仅单独处理动态 key、拼接文案和上下文歧义项。
- 批量完成后统一检查：语言 key 对齐、缺失/重复 key、残留硬编码、类型/lint、相关测试及必要 build；抽样验证关键页面。
- 自动转换存在歧义时，继续完成确定部分并汇总少量待确认项，不反复读取或重做已完成批次。

## 3. 通用工作规则

- 修改前检查仓库状态、目标实现、调用方、配置和相关测试；不凭猜测改代码。
- 以 manifest、锁文件、脚本、配置和相邻代码为事实来源；保持现有架构、命名、风格和技术选型。
- 最小充分改动：只改任务范围，不顺手重构、不格式化无关文件。
- 不覆盖、回滚、暂存或提交无法确认归属的现有改动。
- 未经明确要求，不新增/升级依赖，不创建提交、推送或 PR，不修改 `.env*`、密钥、证书、生产地址和发布配置。
- 不手工编辑生成文件；修改生成源并使用现有脚本重新生成。
- 公共 API、路由、组件输入输出和持久化结构默认保持兼容；破坏性变更必须获得授权。

## 4. 项目识别

只应用命中的技术栈规则：

- Vue：`package.json` 包含 `vue`，通常有 `vite.config.*`。
- Flutter：存在 `pubspec.yaml` 和 `lib/`。
- 微信原生小程序：存在 `app.json`、`project.config.json` 或 `miniprogramRoot`。
- Taro、uni-app 等按实际框架处理，不强套 Vue Web 或微信原生规则。
- Monorepo 先定位本次任务所属 package，再读取其局部配置与指令。

包管理器由锁文件决定，不混用 pnpm、yarn、npm。先读取实际 scripts，不运行臆造的命令。

## 5. 质量、安全与验证

- 处理正常、loading、empty、error 和边界状态；异步逻辑考虑重复触发、竞态、取消与生命周期。
- 外部输入（API、本地存储、URL、平台回调）均不可信，使用前校验；不吞异常或静默伪造成功。
- 不泄露或硬编码 token、密钥、个人信息、生产接口和敏感业务数据；日志与回复须脱敏。
- 不保留 `console.log`、`print`、`debugPrint`、`debugger`、临时开关、占位文案和注释掉的废代码。
- 修复缺陷时，条件允许补充能复现问题的回归测试。
- 验证由小到大：任务文件的格式/静态检查 → 类型或分析 → 相关测试；公共模块、配置、入口或发布相关改动再运行全量检查/build。
- 自动修复与格式化只针对任务文件，并在执行后检查 diff。
- 如检查无法运行或失败，区分本次问题、既有失败和环境限制；如实报告，不声称未执行的检查已通过。

## 6. Vue

- 遵循仓库实际 Vue、TypeScript、Vite、Router、Pinia、样式、i18n 和测试方案，不引入并行方案。
- Vue 3 新代码优先 `<script setup lang="ts">` 和 Composition API；不新增 Options API。
- props、emits、composable、store、API 使用明确类型；禁止裸 `any`，外部数据用 `unknown` 并收窄。
- 不修改 props；派生状态优先 `computed`；watcher、监听器、定时器和 observer 必须正确清理。
- Pinia 解构响应式状态时使用 `storeToRefs`；业务状态变更集中在明确 action/方法中。
- HTTP 复用现有请求层；不在组件内创建重复 axios/fetch 实例，不吞请求错误。
- 用户可见文案使用现有 i18n；新增 key 同步项目要求的语言包。
- 使用稳定列表 key，复用现有设计系统，保证键盘操作、可访问名称、响应式布局和长文本可用。
- 优先运行仓库已有 lint、typecheck 和相关测试；影响入口、路由或构建配置时补跑 build。

## 7. Flutter

- 遵循 `pubspec.yaml`、`analysis_options.yaml` 和现有目录结构，保持 Dart null safety。
- 沿用现有状态管理、路由、网络和持久化方案，不并行引入新框架。
- Widget 职责单一；业务规则进入现有 state/domain/service 层，避免堆在 `build` 中。
- 能合理使用时采用 `const`；异步后使用 context 前检查生命周期，处理取消、重复提交和异常状态。
- 文案进入现有本地化体系；未经要求不修改 bundle id、签名、权限和平台发布配置。
- 测试覆盖纯 Dart 逻辑、状态流和关键 Widget 行为。
- 通常仅对任务文件运行 `dart format`，再执行 `flutter analyze` 和相关 `flutter test`；以仓库脚本为准。

## 8. 微信小程序

- 先区分微信原生、Taro、uni-app 等方案，遵循对应生命周期、目录和构建方式。
- 原生项目保持既有 WXML/WXSS/JS 或 TS 风格及组件通信边界。
- 减少高频、大对象 `setData`，只更新必要路径；卸载/隐藏时清理定时器、监听、订阅和副作用。
- 网络请求复用项目封装，统一处理登录态、超时和错误；不在页面中散落 `wx.request`。
- 微信 API 必须处理失败；区分用户取消、权限拒绝和系统错误。
- 谨慎处理手机号、定位、相册等敏感能力；不修改 AppID、域名白名单、隐私协议、上传版本和项目私有配置。
- 关注主包体积、分包、资源与首屏性能，但性能改造需有测量依据。
- 运行项目已有 lint、typecheck、test/build；需开发者工具人工验证时给出最短验证路径。

## 9. Git 与交付

- 不使用 `git reset --hard`、宽范围 `git checkout --`、`git clean` 或强制推送，除非用户明确授权准确目标。
- 不提交依赖目录、构建产物、覆盖率、日志、trace、临时文件和本地 IDE 配置。
- 用户明确要求提交时，只包含本任务文件并遵循仓库提交规范。
- 最终回复只包含：完成内容、关键变化、实际验证结果，以及存在时的未验证项或风险。简单任务一小段即可。

## 10. 完成定义

- 用户要求的行为已完成，改动最小且无已知回归。
- 相关边界、错误、生命周期、类型/空安全和平台差异已处理。
- 与风险匹配的检查和测试已通过，或未执行原因已说明。
- 最终 diff 无秘密、调试代码、无关格式化、意外锁文件和生成垃圾。
